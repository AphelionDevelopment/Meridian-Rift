# Dogmos IPC DreamDaemon benchmark

This minimal DreamMaker environment measures the benchmark-only `dogmos-byond` shim through
DreamDaemon's real `call_ext` path. It is intentionally separate from `tgstation.dme`: the 512 MiB
diagnostic allocation must never run as part of a normal server or unit-test build.

Run `Prepare-Benchmark.ps1` with the i686 `dogmos_byond.dll` and x86_64 `dogmosd.exe` paths. The
script verifies both PE architectures, stages a self-contained build directory, compiles the DME
with DreamMaker, and prints artifact hashes. Launch and control the resulting DMB through
Meridian-MCP. The emitted markers delimit baseline, scalar latency, typed snapshot/lifecycle/
adjacency/stage latency, bounded service-callback saturation/drain, service-allocation, release,
and completion phases. Sample the exact
DreamDaemon PID and the logged service PID as separate process series; never sum them.

The binding file is generated by the `dogmos-byond` crate and must be regenerated whenever its
benchmark exports change. The shim and service independently hash the service executable, but the
fixture still uses placeholder source-revision and feature-fingerprint values. It is diagnostic
only. Its typed loops exercise the prototype service-owned mixture/adjacency/diffusion path, but do
not establish a production handshake or complete state-migration API. The callback phase fills a
65,536-event queue owned by `dogmosd`, confirms one atomic backpressure rejection, and drains it in
fixed control-payload batches while checking sequence continuity. Those events are diagnostic wire
records, not gameplay callback implementations.
